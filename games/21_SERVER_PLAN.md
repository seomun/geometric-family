# 21. 서버 기획 — 「최저가로 서버를 돌리는 방법」 (퍼블리셔 제출용 초안, 허브 지시 2026-10-12)

> **기획까지만이다. 구현하지 않는다.** 퍼블리셔가 서버비를 부담한다는 전제에서, 지금(서버 없음)부터 단계별로 어디까지 가능한지, 월 비용이 얼마쯤 드는지, 우리 원칙(압박 없음·뽑기 없음·유아 정책·D12 그룹 분리)과 어떻게 맞는지를 적었다. 요금은 **2026-10-12 에 각 서비스 공식 요금 페이지로 확인**했고, 확인하지 못했거나 우리 사용량 가정으로 계산한 값은 **[추정]** 으로 표시했다.
> 한 줄 결론: **지금은 T1(정적 원격 설정, 월 0원)만 하고, 일 활성이 3천~1만을 넘거나 퍼블리셔가 실제 순위표·클라우드 저장을 원하면 T2(Cloudflare Workers + D1, 월 $0~5)로 간다.** 유아 앱은 어떤 단계에서도 개인정보 0 원격 설정 외에는 서버를 쓰지 않는다. 친구·팀(T3)은 하지 않는 것을 권한다.

## 0. 우리 앱 현황 요약 (퍼블리셔용)
- 앱 10종(유아 3: ①놀이터·④색칠북·⑩하루 / 성인 7), 오프라인 HTML5 앱을 Android WebView 로 감쌈. 진행·집·순위(봇)는 **전부 기기 안**(localStorage), 서버·계정 없음.
- 광고(AdMob)만 인터넷을 쓴다(D19). 이미 있는 것: 로컬 순위표(세 가족 봇), 이벤트(시즌 판), 새 소식·FAQ(앱 안 정적), 백업 코드(기기 안 문자열), 광고 제거 구매 자리(상품 ID 없으면 숨김).
- **서버가 있으면 좋아지는 것**: 업데이트 없이 공지·이벤트·광고 빈도 조정(T1), 실제 사람끼리 순위·기기 바꿔도 이어하기(T2), 푸시·분석(T3).

## 2. 비용 추정의 가정(모두 [추정])
- 하루 한 사용자(DAU)당: 앱 시작 때 원격 설정 1~2회(약 5KB), 점수 제출 2회, 순위표 조회 3회(상위 20), 저장 동기화 1~2회(≤ 64KB), 백업 코드 이용은 드묾 → **요청 약 10건/일/DAU**, D1 행 읽기 ≈ 200/일/DAU, 행 쓰기 ≈ 3/일/DAU, 요청당 CPU ≈ 5ms.
- MAU/DAU 비율 3 가정(익명 인증 MAU 과금이 있는 서비스용).

## 4. 원칙과 정책
### 4-1. 유아 그룹(①④⑩) — 서버 정책
- **T1 원격 설정만, 그것도 선택**: 개인정보 0 · 익명 ID 없음 · 요청에 기기 식별자·광고 ID 미포함. 광고 SDK 말고는 이미 INTERNET 이 있으나(D19), 서버 호출을 늘리는 것은 Families 심사 설명 부담이 있어 **기본은 유아 앱 서버 호출 0**을 권한다(필요하면 광고 빈도 비상 스위치 하나만).
- **T2·T3 는 유아 앱에 적용하지 않는다**(순위·저장·푸시·친구 없음). D12 그룹 분리: 서버 DB 도 성인 앱(7개) 전용 스키마, 유아 앱과 키·테이블 공유 없음.
- 이메일·이름·전화·위치·연락처 수집 0. (한국 개인정보보호법상 14세 미만 아동의 개인정보는 법정대리인 동의가 필요 — 유아 앱은 서버 쪽 수집이 없어 동의 절차가 필요 없도록 설계.)
### 4-2. 성인 앱(7)
- **이메일·이름 없이 익명 ID 만**: 앱이 설치 때 만든 랜덤 ID(16바이트)가 전부. 표시 이름은 선택(기본 「세모 아내」 같은 가족 이름 + 숫자, 자유 입력 없음 → 욕설·UGC 신고 문제 회피).
- 순위·저장 데이터는 **삭제 요청 버튼**(설정 → 「내 서버 기록 지우기」)으로 즉시 삭제, 90일 미접속 자동 삭제.
- Play 게임즈를 쓰는 경우 Google 이 플레이어 ID 를 처리(방침 문단 추가).
### 4-3. 개인정보처리방침·Data safety 변경점
| 단계 | 방침 변경 | Data safety 변경 |
|---|---|---|
| T0 | (D19 반영분) 광고 SDK 처리 항목 | 기기 또는 기타 ID·앱 활동·IP 대략 위치(광고) |
| T1 | 「설정 파일을 받기 위해 서버에 접속하며 IP 주소가 서버 로그에 기록된다(최대 N일 보관)」 한 줄 | 변경 없음 또는 「앱 정보 및 성능: 진단」 정도 [확인 필요] |
| T2(성인) | 익명 ID·점수·저장 데이터 수집·보관 기간·삭제 방법·처리 위탁(퍼블리셔가 선택한 클라우드) 문단 | **「기기 또는 기타 ID: 앱 기능 목적·수집(필수 아님/선택)」**, 「게임 활동」 수집, 전송 중 암호화 예, 삭제 요청 가능 예 |
| T3 | 푸시 토큰(FCM)·분석 항목, 법정 보관 | 푸시 토큰·분석 데이터 추가 |
- 유아 앱 방침·Data safety 는 T1 이후에도 변경 없음(서버 호출 0 권장안일 때).
### 4-4. 압박 없음 원칙 — 서버가 생겨도
- **카운트다운·남은 시간·FOMO 문구 금지**, 이벤트는 해마다 순환하고 놓친 것은 「다시 열기」(D21 H5 그대로). 서버 시계는 **날짜 판단용**일 뿐 타이머를 만들지 않는다.
- 순위가 낮아도 불이익 0, 푸시는 하루 1회 이하·기본 꺼짐(H3)·야간 금지, 친구 요청·팀 의무 없음.

## 5. 기술 설계(엔진 `GF.net` 추상층)
### 5-1. 원칙: 서버가 없거나 오프라인이어도 지금처럼 동작
```
GF.net = {
  config: { base: '', key: '', enabled: false },          // 빌드 때 주입(§5-4). base 가 비면 전부 no-op = 지금과 같음
  online(), id(),                                         // 익명 ID(localStorage gf:net:id, 앱 삭제 시 사라짐)
  get(path, {ttl}), post(path, body),                     // 타임아웃 3초 · 실패는 조용히 · 캐시된 값/번들 값으로 대체
  remote(), submit(board, proof), board(boardId, scope), save(blob), load(), vault(code)   // 단계별로 켜짐
}
```
- **오프라인 우선**: 모든 호출은 실패해도 UI 를 막지 않는다. 결과는 기기 안에 먼저 저장하고(현재 구조) 서버는 비동기 후속. 캐시 TTL(원격 설정 6시간).
- **웹판·유아 앱·테스트**: `GF.net.config.enabled=false` → 호출 자체 없음(웹판 no-op).
### 5-2. 기존 코드와의 연결
| 기존 | 서버가 생기면 |
|---|---|
| `GF.ops`(새 소식·FAQ·이벤트 달력·문자열 표) | T1: `GF.data.ops` 를 번들 값으로 시작, 원격 JSON(`/config/<앱>.json`)으로 덮어씀(구조 동일, 서명 필드). 광고 빈도(`GF.ads.config`)·비상 스위치(`adsOff`, `bannerOff`)도 같은 JSON |
| `GF.rank`(내 기록·세 가족 순위·봇) | T2: `record()` 가 점수 제출 → 서버 점수 있으면 **실제 순위 + 봇 혼합**(사람이 적을 때 봇이 채움), 오프라인이면 지금처럼 봇. 보드 id 는 D16 의 6개 그대로 |
| `GF.board`(Play 게임즈 브리지) | Play 게임즈를 쓰면 브리지가 그대로, 자체 서버를 쓰면 `GF.net` 이 대신(둘 다 하면 중복 제출 방지 플래그) |
| `Room` 저장(`gf:house:*`)·앱 저장(`gf:<앱>:*`) | T2 클라우드 저장: **백업 코드와 같은 직렬화**(`GF.ops.makeCode` 의 키 집합)를 서버에 `PUT /save/<id>`(버전·체크섬), 충돌은 「새 기록이 이김 + 이전 것은 백업 슬롯 1개」 |
| 백업 코드(기기 안) | T2: 「서버에 보관」 선택 시 8자리 짧은 코드(90일), 코드로 다른 기기에서 복원 |
| 복귀 선물·금요일 선물·미션 | 기기 날짜 기준 유지(서버 시계 의존 없음) |
### 5-3. 부정행위(점수 조작) 최소 대책
1) **서버가 점수를 재계산**: 오늘의 한 판·끝없이는 시드가 결정적이라(우리 생성기·코어는 순수 JS) 클라이언트가 **수 목록(moves)** 을 제출하고 Worker 가 같은 코어로 재생해 점수·유효성을 계산 → 점수 값 자체를 믿지 않음. (이미 `botPlay` 가 같은 점수식을 쓴다.)
2) 제출 한도(ID 당 보드·날짜 1~N회), 점수 상·하한, 시간 창(오늘 날짜의 시드만), ID 생성 직후 가중치 낮춤.
3) 선택: **Play Integrity API** 토큰을 제출에 붙여 변조 앱·에뮬레이터를 거름(Google 무료, 서버 검증 필요).
4) 완벽한 방어는 아님 — 캐주얼 순위표 수준으로 충분하다고 가정, 신고·삭제 수단 둠.
### 5-4. 퍼블리셔 계정·키 주입(저장소에는 넣지 않음)
- Cloudflare 계정은 **퍼블리셔 소유**, `wrangler` 비밀값(서명 키·D1 바인딩)은 퍼블리셔 계정에만 존재. 우리 저장소에는 서버 코드(`server/`)와 설정 예시만.
- 앱에는 **공개 값만**: 기본 URL·앱 공개 키·(원격 설정 서명 검증용 공개 키). `~/.gradle/gradle.properties` 의 `GF_NET_BASE_<FLAVOR>`(+선택 `GF_NET_PUBKEY`) 를 AdMob ID 와 같은 방식으로 `BuildConfig` → `window.GFOps.netInfo()` → `GF.net.config`. 값이 없으면 서버 기능은 숨김(광고 제거 구매와 같은 규칙).
- 유아 flavor 는 빌드 시 `GF_NET_*` 를 무시(Java 에서도 방어).
### 5-5. 운영
- 모니터링: Cloudflare 대시보드(요청·에러), 일일 요청 상한 경보. 비용 상한: 계정 결제 한도(알림) 설정.
- 장애 시: 앱은 오프라인으로 계속 동작(번들 값 사용). 점검 공지는 T1 JSON 한 줄.

## 6. 권장안과 퍼블리셔가 정할 것
**권장안(1개)**: 
1. **지금 T1 만**: 정적 원격 설정(Cloudflare Pages). 월 0원. 공지·이벤트·광고 빈도를 업데이트 없이 운영.
2. **Play 게임즈를 먼저 시험**(작가 계정·순위표 6개 준비 후): 순위표·저장을 서버비 0 으로 얻는 길(성인만).
3. **일 활성 약 3천~1만 명 또는 퍼블리셔가 자체 순위·클라우드 저장을 원할 때 T2**(Cloudflare Workers + D1, 월 $0~5). 서버가 점수를 재계산해 조작 방지.
4. **T3(친구·팀·푸시·분석)는 하지 않는다**(원칙 충돌·비용·운영 부담). 푸시는 로컬 알림(H3)으로 대체.

- 비용은 우리 사용량 **가정**으로 계산한 **[추정]** 이다. 실제 요청 수는 앱 설계(캐시·호출 빈도)와 사용 패턴에 따라 달라진다. Firebase 의 문서 단위 읽기 단가는 이번에 공식 숫자를 확인하지 못했다.

- 기획만 했고 프로토타입·부하 시험을 하지 않았다.
